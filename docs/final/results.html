What the four changes did네 가지 변경이 한 일

All four stages from the proposal are built, as opt-in changes that leave demo, verify, misuse and the HW7 numbers exactly as they were. One change worked: when both owners disclose the order of their priorities, deals close more often and capture more of the available surplus. It closes the efficiency gap to price-only negotiation but does not beat it, and the gain leans toward the tougher side. MESO did nothing measurable.

제안서의 네 단계를 모두 구현했어. 전부 opt-in이라 demo, verify, misuse, HW7 숫자는 그대로야. 효과가 있었던 건 하나: 양쪽 주인이 우선순위 순서를 공개하면 성사율이 오르고, 가능한 잉여를 더 많이 가져간다. 가격만 협상한 경우와의 효율 격차는 메웠지만 넘어서지는 못했고, 늘어난 몫은 더 강경한 쪽으로 기운다. MESO는 측정 가능한 효과가 없었어.

How far these numbers go이 숫자들의 한계

  • Rule agents only. No Claude agent has run with MESO or disclosure. The MCP tools describe both, but whether an LLM uses a disclosed order well is untested.
  • 규칙 기반 에이전트만. Claude 에이전트로는 MESO나 공개를 돌려본 적이 없어. MCP 도구 설명에는 들어가 있지만, LLM이 공개된 순서를 잘 쓰는지는 미검증이야.
  • Multiple comparisons. The analysis runs 56 tests; none survives a Bonferroni threshold (p < 0.0009) on its own. Disclosure versus fix was the effect the proposal set out to find, its intervals clear zero in both market types and on all three seeds, and it is the one to report as primary. Treat the rest as exploratory.
  • 다중 비교. 검정이 56개라 Bonferroni 기준(p < 0.0009)을 단독으로 넘는 건 없어. 공개 대 fix는 제안서가 찾으려던 효과이고, 두 시장 유형과 시드 3개 모두에서 구간이 0을 넘지 않으니 이걸 주 결과로 보고하고, 나머지는 탐색적이라고 적는 게 맞아.
  • Untested in the product. The Postgres store against a live database, and signing a mandate end to end from the new builder (needs Clerk sign-in). Everything else is covered by 72 tests and next build.
  • 제품에서 미검증. 실제 Postgres DB, 그리고 새 위임장 화면에서 서명까지의 전체 흐름(Clerk 로그인 필요). 나머지는 테스트 72개와 next build로 확인했어.

What to review, in order리뷰 순서

Four stacked PRs; each diff contains only its own stage. Every behaviour change is off by default.PR 네 개가 사슬로 쌓여 있고, 각 diff에는 자기 단계만 들어 있어. 모든 동작 변경은 기본값이 꺼짐이야.

#5 MESO

Look at the accept path. Each alternative gets its own JANG-minted offerId; accepting a multi-package offer must name one (AMBIGUOUS_ACCEPT otherwise). The agreement carries that offerId and its terms, so AgreementBodySchema and signing are unchanged. Alternatives sit inside the offer rather than as separate rows, so one turn stays one round everywhere.

수락 경로를 봐줘. 대안마다 JANG이 offerId를 발급하고, 패키지가 여럿인 제안을 수락할 땐 하나를 지정해야 해(아니면 AMBIGUOUS_ACCEPT). 합의서에는 그 offerId와 terms가 들어가서 AgreementBodySchema와 서명은 그대로야. 대안은 별도 행이 아니라 offer 안에 넣어서, 한 턴이 어디서나 한 라운드로 유지돼.

#6 Priority disclosure우선순위 공개

Look at what owners sign. MandateBody.disclosePriorities is optional with no default, so old mandates keep the same body and signature. redactSessionFor adds keys in order and nothing else; leak tests were written first.

주인이 서명하는 대상을 봐줘. MandateBody.disclosePriorities는 기본값 없는 optional이라 기존 위임장의 본문과 서명이 그대로야. redactSessionFor는 순서대로 나열한 키만 추가하고, 유출 테스트를 먼저 썼어.

#7 Pareto frontierPareto 프론티어

Look at the one departure from the proposal. "No deal is possible" and "here is a better package for both" go to the operator only, never to agents. Telling agents would let one re-lodge its own mandate, reopen, and binary-search the other side's limit. Also: the HW7 search now lives in src/lib/jang/frontier.ts (rows identical), items are capped at five terms, and the cache sits outside Session.

제안서와 달라진 한 가지를 봐줘. "합의 불가능"과 "양쪽 다 더 나은 패키지"는 운영자에게만 가고 에이전트에게는 안 가. 에이전트에게 알리면 자기 위임장을 바꿔 재등록하고 세션을 다시 여는 식으로 상대 한계를 이진 탐색할 수 있어서야. 그 밖에: HW7 탐색 코드를 src/lib/jang/frontier.ts로 옮겼고(행 단위 동일), 항목은 5개로 제한, 캐시는 Session 밖에 있어.

#8 Alternative, not a number숫자 대신 대안

The builder asks "which would you rather have" (at most five questions for four terms) and "what would you do instead," and derives weights and the reservation value. utility() scoring is unchanged. This PR also carries the significance script.

위임장 화면이 "어느 쪽이 낫나요"(항목 4개면 최대 5문항)와 "안 되면 어떻게 하실 건가요"를 묻고, 가중치와 유보값을 유도해. utility() 점수 계산은 그대로야. 유의성 분석 스크립트도 이 PR에 있어.
