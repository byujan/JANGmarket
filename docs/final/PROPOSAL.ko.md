## 1. 왜 지금 이걸 해야 하나

우리 해자는 매칭이 아닙니다. **JANG이 양쪽의 권한을 동시에 보는 유일한 당사자**라는 점입니다.
그 자리에 있으면 상대편 에이전트는 절대 못 하는 두 가지를 할 수 있습니다.

1. **낭비를 남기지 않는다.** 한쪽이 손해 보지 않고는 다른 쪽이 더 가져갈 수 없는 지점을 찾는다.
2. **나눔이 한쪽으로 쏠리지 않게 한다.** 한 사람이 다 가져가는 걸 막는다.

HW7을 보면 **두 번째는 이미 되고 있습니다.** 구매자가 가져가는 잉여 비율이 JANG에서 **0.55**,
가격만 협상에서 **0.27**입니다. 협상이 약한 쪽을 지켜주고 있습니다.

그런데 **첫 번째는 안 되고 있습니다.** 이 제안서가 노리는 게 그겁니다.

지금 우리는 그 특권적 위치를 **금지하는 데만** 씁니다. **좋게 만드는 데는** 안 씁니다.
한 문장으로 말하면 그게 전부입니다.

## 4. 네 가지 변경

전부 이름 있는 기법이지 발명이 아닙니다. 그리고 전부 **opt-in, 기본값 꺼짐**입니다.
`respectBounds`를 넣었던 방식 그대로입니다.

### 1단계: 제안 하나 대신 세 개

**MESO**(동일 가치 복수 제안)는 실무에서 늘 쓰는 기법입니다. 나한테 가치가 같은 패키지를 여러 개
내놓고 상대가 고르게 합니다. 상대의 선택이 우선순위를 알려주는데, **나는 아무것도 잃지
않습니다.** 어차피 나한테는 다 같았으니까요.

`bestCounter`는 이미 후보 전체를 훑고 있습니다. 지금은 그중 하나를 집습니다. 목표 효용을 넘는
것들 중에서 **서로 최대한 다른 세 개**를 집게 바꾸자는 겁니다.

TV 시나리오로 돌려본 결과입니다. **판매자에게 전부 0.56으로 같은** 세 패키지:

| 패키지 | 판매자 | 구매자 |
| --- | --- | --- |
| $1,220 · 1일 배송 · 36개월 · 사운드바 없음 | 0.554 | **0.508** |
| $1,130 · 28일 배송 · 18개월 · 사운드바 없음 | 0.559 | 0.347 |
| $1,250 · 26일 배송 · 12개월 · 사운드바 포함 | 0.565 | 0.236 |

**판매자는 셋을 구분하지 못합니다.** 구매자에게는 두 배 차이가 납니다.

지금 데모 합의가 구매자 0.486 / 판매자 0.560입니다. 첫 번째 줄은 구매자 0.508 / 판매자
**0.554**입니다. 구매자가 0.022 얻고 판매자가 0.006 내놓습니다. **교과서적인 맞교환인데 지금
구조로는 못 찾습니다.**

**세 개는 에이전트가 만들고 상대 에이전트가 고릅니다. 사람은 여기 안 들어옵니다.** 주인은
위임장을 쓰면 할 일이 끝납니다.

| 파일 | 변경 |
| --- | --- |
| `src/lib/jang/types.ts` | `Offer`에 `alternatives?: Terms[]` 추가, 최대 2개 |
| `src/lib/jang/session.ts` | `submitOffer`가 **대안 각각도** 검사. `acceptStandingOffer`가 어느 것인지 받음 |
| `src/app/api/sessions/[id]/offers/route.ts` | 대안 통과 |
| `src/app/api/sessions/[id]/accept/route.ts` | 특정 패키지를 수락 |
| `mcp/server.ts` | `offer`·`counter`에 대안 인자, `accept`에 선택 인자 |
| `db/schema.sql` | `offers`에 `alternatives jsonb` |
| `src/lib/store/*` | 양쪽 구현. 공용 적합성 테스트가 일치를 보장 |
| `agents/rule-strategy.ts` | `bestCounter`가 서로 다른 세 개를 반환 |
| `src/components/LiveNegotiation.tsx` | 사다리에 세 칸 |

> **Peter 결정 사항.** 이제 수락할 때 **어느 패키지인지 말해야** 합니다. 지금
> `acceptStandingOffer(session, agentId)`는 "서 있는 제안"을 받는데, 셋이 올라가 있으면
> 모호해집니다. **모호한 수락은 모호한 서명 합의서**가 됩니다. 인덱스보다 명시적인 offer
> 참조를 넘기는 쪽을 제안합니다.

### 2단계: 입장이 아니라 이해관심

*Getting to Yes*의 한 줄 요약은 "입장이 아니라 이해관심을 말하라"입니다. 그런데 **위임장에 이미
둘 다 있습니다.** 하드 바운드가 입장이고 가중치가 이해관심인데, 상대에게는 **입장만** 갑니다.

주인이 **순서만** 공개할 수 있게 하고 싶습니다.

```
["warrantyMonths", "price", "deliveryDays", "bundle"]
```

가중치 없음. 한계선 없음. 유보값 없음. opt-in, 기본 꺼짐.

상대 에이전트가 이 순서를 `distanceToTheirAsk`의 가중치로 쓰면, 처음으로 **상대가 서 있는
자리**가 아니라 **상대가 중요하게 여기는 쪽**으로 움직입니다.

| 파일 | 변경 |
| --- | --- |
| `src/lib/jang/types.ts` | `MandateBody`에 `disclosePriorities?: boolean` |
| `src/lib/jang/session.ts` | `redactSessionFor`가 공개 시 순서만 내보냄 |
| 테스트 | 기존 유출 테스트 옆에 새 테스트. 공개해도 숫자는 하나도 안 샌다 |
| `agents/rule-strategy.ts` | 공개된 순서로 `distanceToTheirAsk`에 가중치 부여 |
| `src/components/MandateBuilder.tsx` | 체크박스 하나 |

> **Peter 결정 사항.** 이건 **주인이 서명하는 대상이 바뀌는** 변경입니다. 기존 위임장이 계속
> 검증되려면 optional에 기본값이 있어야 합니다.

### 3단계: 숫자 말고 대안을 묻자

"당신의 유보 효용이 얼마입니까"에 답할 수 있는 사람은 없습니다. 실제 협상에서는 그렇게 묻지
않습니다. **거래가 깨지면 어떻게 할 건지**를 묻고, 기준선은 거기서 따라 나옵니다.

```
질문    "여기서 못 사시면 어떻게 하실 건가요?"
답      "다른 데서 $1,280에 12개월 보증, 일주일 배송으로 살 수 있어요."
유도    reservationUtility = utility(그 패키지, 이 위임장)
```

TV 시나리오로 재봤습니다.

| 주인이 말한 대안 | 자동 유도된 기준선 |
| --- | --- |
| "$1,280, 12개월, 7일" | 0.113 |
| "$1,250, 24개월, 14일" | 0.278 |

**주인은 숫자를 한 번도 안 봅니다.** 같은 화면에서 중요도 슬라이더도 **완성된 패키지 중 고르는
질문 3~5개**로 바꿉니다. 컨조인트 분석이 가중치를 잡아내는 방식 그대로입니다. TV 기준으로
슬라이더 9개가 질문 5개 정도로 줄어듭니다.

새 파일은 `src/lib/jang/elicit.ts` 하나뿐이고, 기존 `utility()`를 호출만 합니다. **엔진은 안
건드립니다.** 그리고 엔진이 카테고리를 모르니까 **질문 생성기도 몰라도 됩니다.** `ItemSpec`만
있으면 되니 케임브리지 임대에도 코드 수정 없이 그대로 돌아갑니다.

### 4단계: 프론티어를 제품으로

`Pareto`가 `scripts/hw7/`에만 있습니다. **JANG은 자기 거래가 좋은지 모른 채 돌아갑니다.**
이 코드를 `src/lib/jang/frontier.ts`로 끌어올리고 싶습니다.

이게 싼 이유가 있습니다. **프론티어는 위임장 두 개의 함수이지 제안의 함수가 아닙니다.**
위임장은 세션이 열릴 때 고정되니, **세션당 한 번** 계산하고 그 뒤로는 읽기만 합니다.

전수 생성부터 효용 계산, 필터링, 프론티어 추출까지 전부 포함해 재봤습니다.

| 시나리오 | 항목 | 패키지 | 프론티어 | 시간 |
| --- | --- | --- | --- | --- |
| `tv-clearance` | 4개 | 7,800 | 148 | **6 ms** |
| `cambridge-rental` | 5개 | 2,660 | 62 | **2 ms** |

TV 격자로 외삽하면 최악의 경우 **5개 항목 약 77 ms, 6개 약 850 ms, 7개 약 9초**입니다.
그래서 **협상 가능 항목을 5개로 제한**하자는 겁니다. `ItemSpecSchema`에 한 줄이면 됩니다.
`cambridge-rental`이 이미 정확히 5개라서 **기존 시나리오가 안 깨지고, 스트레스 케이스도 이미
확보**돼 있습니다.

(프론티어는 전수 비교 말고 정렬 스윕으로. 목표가 2차원이라 정렬 한 번, O(n log n)입니다.)

쓰이는 곳이 네 군데입니다.

| 시점 | 하는 일 |
| --- | --- |
| **세션 열릴 때** | feasible 집합이 비었으면 **어떤 협상을 해도 불가능**하다는 뜻. 12라운드 태우지 말고 0라운드에 알린다. HW7의 no-ZOPA가 시드당 20개 시장에서 정확히 그 짓을 했고, Claude 에이전트면 그게 **돈**이다. 60번 협상에 $84.08 썼다 |
| **협상 중** | `/admin`에 프론티어와 현재 위치를 그린다. 그 화면은 이미 양쪽 위임장을 보여주니 새로 새는 게 없다. 교착 감지도 된다 |
| **서명 직전** | 지금 안보다 **양쪽 다** 더 나은 패키지가 있으면 제시한다. 한쪽이라도 거부하면 원래 안이 그대로 성립하므로 **아무도 손해 볼 수 없다** |
| **협상 후** | 합의서에 효율과 프론티어 거리를 기록한다. 그러면 언젠가 벤치마크 숫자가 아니라 **실제 운영 숫자**를 말할 수 있다 |

> **절대 하면 안 되는 것.** JANG이 프론티어로 에이전트의 제안을 **거르거나 재정렬하면 안
> 됩니다.** 뭐가 통과했는지만 봐도 상대 선호를 역추적할 수 있어서 검열이 무력화되고, JANG이
> 중립자가 아니라 한쪽의 협상 대리인이 됩니다. 프론티어는 **양쪽이 거부할 수 있는 제안**에만
> 쓸 수 있습니다.

## 5. 안 건드리는 것

| 그대로 | 이유 |

| `src/lib/jang/utility.ts` | 점수 계산을 바꾸면 HW7과 비교가 불가능해짐 |

| Ed25519 서명, 합의서 본문 | `npm run verify`가 그대로 통과해야 함 |
| 기본 검열 동작 | 오늘 안 새는 건 내일도 안 새야 함 |
| 엔진의 카테고리 무지 | 케임브리지 임대에 코드가 안 든 이유 |
| 카테고리 템플릿 | 범위 밖, 8장 참고 |

**모든 동작 변경은 opt-in이고 기본값은 꺼짐입니다.** 플래그를 켜지 않는 한 `npm run demo`,
`npm run verify`, `npm run misuse`는 **오늘과 똑같이** 동작합니다.

## 9. Peter가 결정해줘야 할 것

1. **`Offer.alternatives`, 최대 2개.** offer 스키마를 늘리는 게 괜찮은지, 아니면 다른 데
   둘지.

## 10. 요약

**JANG의 차별점은 매칭이 아니라 협상입니다.** 우리는 협상할 안전한 판을 만들었습니다.
아직 협상 자체는 안 만들었습니다.

HW7은 JANG이 가격만으로는 닿지 못하는 거래를 성사시킨다는 걸 증명했고(**81% 대 53%**),
그 거래가 양쪽에게 더 낫다는 건 증명하지 못했습니다(**효율 0.80 대 0.84**). 원인은 아이디어가
아니라 **우리 에이전트**로 보입니다. 상대 우선순위를 끝내 모른 채 상대가 서 있는 자리로만
다가가고, 우리 첫마디가 던지는 질문의 답은 아무도 읽지 않습니다.

네 가지 변경. 전부 표준 기법이고, 전부 opt-in에 기본 꺼짐입니다.

| | 변경 | 효과 |
| --- | --- | --- |
| **1** | 같은 가치의 제안 세 개 | 상대의 선택이 우선순위를 공짜로 알려줌. 판매자에게 똑같은 세 패키지가 구매자에겐 0.508 / 0.347 / 0.236 |
| **2** | 우선순위 **순서만** 공개 | 상대가 실제로 중시하는 쪽으로 맞바꿀 수 있게 됨 |
| **3** | 유보값 대신 **대안**을 질문 | 기준선이 자동 유도. 주인이 "0.30"을 안 봄 |
| **4** | Pareto 프론티어를 제품으로 | 항목 5개 상한에서 세션당 77ms. 불가능한 협상을 0라운드에, 낭비된 거래를 서명 직전에 잡음 |

효용 함수, 위임장 검사, 서명, 기본 검열은 **하나도 안 건드립니다.** 측정은 전부 기존
하네스(77초)로 하고, **Claim A와 Claim B를 항상 같이 봅니다.**

**9장에 질문 여섯 개가 있습니다. 1·2단계는 Peter 코어라서 답을 받기 전에는 시작하지
않겠습니다.**
